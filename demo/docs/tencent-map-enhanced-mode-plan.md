# 灵山胜境腾讯地图增强模式设计方案

## 1. 设计目标

腾讯地图增强模式不是替代 `/scenic-3d-map`，而是作为真实地理底座，用于承接现场导航、真实坐标、POI 聚焦和路线兜底。

当前项目应保持双地图模式：

- 3D 导览模式：页面为 `/scenic-3d-map`，沉浸式、艺术化，适合展示、讲解、路线故事和文化体验。
- 真实地图模式：页面为 `/map`，准确性优先，适合导航、定位、纠偏和现场使用。

两者通过以下稳定标识打通：

- `poiId`
- `sceneRoute`
- `guideRoute`
- `routeGeometry`

职责划分：

- `/map` 负责真实地图、真实坐标、POI 聚焦、路线兜底、实时定位和导航。
- `/scenic-3d-map` 负责沉浸式视觉导览、路线故事和艺术化体验。

## 2. 为什么需要腾讯地图增强模式

腾讯地图底图自带道路、水体、建筑轮廓、地名等真实地理信息。对于道路和水体，直接基于腾讯地图显示通常比完全手工构建 3D 表达更可靠，尤其适合现场导航、POI 聚焦和路线确认。

但腾讯地图底图中的道路、水体和建筑主要是渲染服务的一部分，不等于项目可以直接批量提取完整矢量道路网、水体 polygon 或建筑轮廓数据。

因此增强模式应采用：

> 腾讯底图 + 项目自有图层叠加

而不是：

> 从腾讯底图抓取全部道路、水体和建筑矢量数据

增强模式的重点是把项目自有 POI、routeGeometry、调试图层、实时定位和导航状态叠加到腾讯底图上，让真实地图页从“可看路线”升级为“可诊断、可导航、可兜底”的真实地理工作台。

## 3. /map 当前已有能力盘点

当前 `/map` 已具备以下能力：

- 腾讯地图 GL JS 加载。
- POI Marker 渲染。
- route Polyline 渲染。
- InfoWindow 展示。
- route switch 路线切换。
- `/map?poi=xxx` 自动聚焦指定景点。
- `/map?sceneRoute=xxx` 映射真实 `guideRoute`。
- `debugSceneRoute` 调试叠加层。
- `plannedRoute` 诊断字段展示。
- Tencent walking path JSON 复制。
- Tencent walking path JSON 下载。
- `routeGeometry` candidate 数据生成流程。

当前 `/map` 已经能作为真实地图底座，但还缺少系统化的图层开关、实时定位、路线进度、偏航判断和导航状态表达。

## 4. 腾讯地图增强模式的图层设计

### 4.1 底图层

- 使用腾讯地图底图。
- 显示真实道路、水体、建筑、地名。
- 不做二次提取。
- 只作为视觉与导航底座。

底图层应保持稳定，不应被 3D 风格化图层覆盖。用户需要在这里获得真实地理判断。

### 4.2 POI 图层

数据来源：

- `lingshanPois`
- `guideSpots`

Marker 分类建议：

- 核心景点。
- 广场 / 观景点。
- 入口 / 出口。
- 服务设施。
- 未来厕所 / 观光车站点。

位置策略：

- `displayLocation` 用于地图展示。
- `navLocation` 用于真实导航终点。
- 核心点优先校准 `navLocation`。

重点：

- 大佛、梵宫、九龙灌浴、五印坛城、祥符禅寺等大体量景点不能直接把建筑中心作为导航终点。
- `navLocation` 应落在入口、广场、可步行到达点或观赏区边缘。

### 4.3 路线图层

路线图层建议分层显示：

- 当前 `guideRoute` 的腾讯 walking route。
- `routeGeometry` candidate / verified 路线。
- `sceneRoute` 骨架调试线。
- 当前路线高亮线。
- 后续已走 / 未走路线分层。

建议展示规则：

- 默认显示当前真实路线。
- 调试模式显示 sceneRoute 骨架线和诊断信息。
- verified routeGeometry 可作为未来真实地图展示层。
- candidate routeGeometry 只能作为候选参考，不应对用户宣称已人工核验。

### 4.4 调试图层

调试图层只在 debug 参数开启时显示。

已有能力：

- `debugSceneRoute`
- `plannedRoute` 诊断卡片。
- `usedFallback`
- `fallbackReason`
- `path.length`
- walking path JSON 复制 / 下载。

后续可增加：

- 路线段级诊断。
- segment path 导出。
- routeGeometry 对比开关。
- candidate / verified 状态显示。

### 4.5 实时定位图层

后续增强：

- 用户当前位置 Marker。
- GPS 精度圆。
- 路线最近点吸附。
- 下一站提示。
- 偏航提示。
- 地图自动跟随开关。

该图层是腾讯地图增强模式的核心，不应放到 `/scenic-3d-map` 中承担精确导航。

### 4.6 导航辅助图层

后续增强：

- 下一站方向。
- 到下一站距离。
- route progress。
- 重规划到下一站。
- 返回 3D 导览模式。

建议将这些信息放在地图上的导航状态卡片中，而不是改动底图本身。

## 5. 道路与水体数据策略

### 道路

当前可获得：

- 某次腾讯 walking route 返回的 `path`。
- 多条 `routeGeometry` candidate。
- 通过多个相邻 POI 路线请求采样出的候选道路网络。

当前不可直接获得：

- 景区完整道路网。
- 全部道路节点 / 道路边。
- 腾讯底图中的内部道路矢量数据。

推荐策略：

1. 当前继续使用 `routeGeometry` candidate。
2. 后续通过相邻站点 pair 导出 segment path。
3. 将多个 segment path 合并成候选 road network。
4. 人工复核后标记 `verified` 或 `hybrid_corrected`。

这样可以逐步形成项目自己的候选道路网络，而不是依赖不可导出的底图矢量。

### 水体

腾讯地图中可以看到水体显示。

但不应假设项目可以直接获取：

- 太湖 / 景区水体 polygon。
- 湖岸线 GeoJSON。
- 底图水系矢量数据。

推荐策略：

- `/map` 使用腾讯底图直接显示真实水体。
- `/scenic-3d-map` 第一版使用艺术化水面意象。
- 后续如需要更精确，可人工描边或引入官方 / 合规来源的水体多边形。

## 6. 3D 地图与腾讯地图增强模式的关系

两者不是互斥关系，而是互补关系。

`/scenic-3d-map` 负责：

- 主视觉。
- 沉浸式游览。
- 文化路线讲述。
- 建筑和景点符号化表达。
- 展示、答辩、轻导览。

`/map` 负责：

- 真实底图。
- 真实路线。
- 实时定位。
- POI / `navLocation`。
- 现场导航和纠偏。

交互流：

1. 3D 选景点 -> `/map?poi=xxx`
2. 3D 选路线 -> `/map?sceneRoute=xxx`
3. 真实地图查看完 -> 返回 `/scenic-3d-map`
4. 未来可在 `/map` 中增加“进入 3D 导览模式”按钮

## 7. 实时导航功能分阶段设计

### 阶段 A：当前位置显示

- 使用 `navigator.geolocation`。
- 显示用户位置 Marker。
- 显示 GPS accuracy circle。
- 增加地图自动跟随开关。

验收重点：

- 手机端能授权定位。
- 位置 Marker 能稳定更新。
- 精度圆能反映定位质量。

### 阶段 B：路线进度

- 计算用户位置到 `routeGeometry` 最近点。
- 计算路线进度百分比。
- 计算下一站。
- 显示距离下一站多少米。

验收重点：

- 用户在路线附近移动时，进度单调推进。
- 下一站提示符合 route sequence。
- 距离计算结果可读且稳定。

### 阶段 C：偏航判断

- 用户距离当前路线超过阈值时触发候选偏航。
- 建议初始阈值为 30m。
- 连续多次偏离后提示。
- 提供重新规划到下一站按钮。

验收重点：

- 不因 GPS 抖动频繁误报。
- 偏航提示不打断普通浏览。

### 阶段 D：重规划

- 调用腾讯 walking route：
  - 用户当前位置 -> 下一站 `navLocation`
- 显示临时 reroute 线。
- 到达下一站后恢复主 `routeGeometry`。

验收重点：

- 临时路线和主路线视觉区分明确。
- 重规划失败时有兜底提示。

### 阶段 E：3D 同步

- 将用户真实 lat/lng 通过 `geoToScenePosition` 映射到 `/scenic-3d-map`。
- 3D 中只显示大致位置和导览进度。
- 精确导航仍以 `/map` 为准。

验收重点：

- 3D 位置表达不误导用户为精确导航。
- 3D 只承担进度和空间理解辅助。

## 8. navLocation 校准策略

`displayLocation` 用于展示景点，`navLocation` 用于真实导航终点。

大景点不能直接用建筑中心点导航。灵山大佛、梵宫、九龙灌浴、五印坛城、祥符禅寺应优先校准 `navLocation`。

`navLocation` 应放在：

- 入口。
- 广场。
- 可步行到达点。
- 观赏区边缘。

| POI | 当前问题 | navLocation 建议 | 优先级 |
|---|---|---|---|
| 灵山大佛 | 建筑 / 景点中心不一定是可到达导航终点 | 放在佛前广场、台阶入口或游客可到达平台 | 高 |
| 九龙灌浴 | 水景中心点不适合作为导航终点 | 放在观赏区边缘或广场可达点 | 高 |
| 梵宫 | 建筑体量大，中心点可能落在建筑内部 | 放在梵宫入口或梵宫广场可达点 | 高 |
| 五印坛城 | 坛城中心与入口可能不同 | 放在入口或近路网可达点 | 高 |
| 祥符禅寺 | 寺院范围可能较大 | 放在寺院入口或主要参观点入口 | 高 |
| 南门入园 | 需要区分展示门楼和真实入园 / 检票点 | 放在检票口、入园口或游客实际通过点 | 高 |
| 景区出口 | 需要区分出口标识和真实离园通道 | 放在真实出口通道或可达出口节点 | 高 |

## 10. 风险与注意事项

- 不要把腾讯底图误认为可导出矢量数据。
- 不要把 candidate `routeGeometry` 说成 verified。
- 实时定位在浏览器中存在权限和精度问题。
- 手机端性能和 WebGL 要实机验证。
- 腾讯地图 Key 不应提交。
- `navLocation` 不校准会导致导航体验差。
- 3D 地图不应承担精确导航责任。
- 水体边界第一版只能作为意象表达，除非有合规边界数据来源。

## 11. 结论

腾讯地图增强模式适合作为真实底图和导航主模式。3D 地图适合作为沉浸式导览主视觉。

未来产品应采用“双地图模式”：

- 3D 导览模式负责体验。
- 真实地图模式负责导航。

道路和水体可以在腾讯底图上自然显示，但不能直接从底图中提取完整矢量数据。

下一步应先设计 `/map` 增强模式 UI，再做实时定位。
