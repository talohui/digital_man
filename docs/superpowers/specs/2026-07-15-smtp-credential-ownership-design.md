# SMTP 凭据与运营发送计划职责拆分设计

## 目标

将 B 端的邮件配置按职责拆分：服务配置页只维护发件人邮箱与 QQ SMTP 授权码；运营报告页维护收件人、日报/周报开关、发送时间、测试邮件和发送记录。

## 现状与问题

服务配置页和运营报告页都展示收件人及日报/周报计划。两个页面使用同一个综合更新请求，导致用户不知道应该在哪个页面维护发送计划，也增加了保存时互相覆盖的风险。

## 设计

### 服务配置页

- 保留 QQ SMTP 配置状态、发件人邮箱、授权码输入框和保存按钮。
- 保留“前往运营报告”链接，作为发送计划的唯一入口。
- 移除收件人输入、收件人标签、日报/周报开关与时间、发送计划说明及相关本地状态。
- 保存时调用独立 SMTP 凭据接口，只提交发件人邮箱和非空授权码；不会触碰收件人或发送计划。

### 运营报告页

- 继续作为收件人和日报/周报发送节奏的唯一配置入口。
- 保留现有收件人校验、计划校验、测试邮件和审计记录功能。
- 发送计划保存请求不携带 SMTP 凭据，避免无意修改发件账号。
- 页面只展示 SMTP 状态摘要，不提供重复的凭据编辑控件。

### 后端接口与数据流

- 新增管理员鉴权的 SMTP 凭据更新接口。
- 接口只更新 `smtpUsername` 和加密后的 `encryptedSmtpAuthCode` 字段，不改动收件人与计划字段。
- 既有综合设置接口继续服务运营报告页的计划保存，并保留兼容旧调用的请求结构。
- SMTP 状态读取继续由现有设置读取接口返回；授权码永不返回前端。

## 错误处理与安全

- 发件人邮箱沿用后端邮箱格式校验。
- 授权码为空表示保持原值；未配置加密主密钥时返回明确的配置错误。
- 页面不回显授权码，也不在日志或响应中输出授权码。
- 保存 SMTP 凭据成功后只清空授权码输入框，保留发件人邮箱和状态。

## 验证标准

- 服务配置页源码和界面不再包含收件人、日报、周报控件。
- 运营报告页仍可增删收件人、修改日报/周报计划并保存。
- SMTP 独立保存请求不会携带或覆盖发送计划字段。
- 后端接口测试证明只更新 SMTP 字段，且授权码以加密形式持久化。
- 前端单元测试、类型检查和生产构建通过。
