# 统一小灵会话与位置感知 RAG 设计

日期：2026-07-10

## 1. 背景

当前游客端按 `spot:<routeId>:<spotId>` 创建独立聊天场景，悬浮“问小灵”又使用独立的 `assistant` 场景。因此游客从地图、景点讲解页和悬浮入口进入时，会看到不同会话和不同页面；切换景点还会丢失连续对话体验。

同时现有聊天 UI 存在三个直接问题：收到回复后发送状态可能不释放、移动端发送按钮图标被 CSS 隐藏、用户担忧/困惑状态会被 Fay 的通用 `Thinking/Speaking` 状态覆盖。

## 2. 目标

1. 游客端只保留一段连续的“小灵导览会话”。
2. 每轮提问都携带最新路线、景点和位置来源，避免使用过期场景。
3. RAG 优先检索当前景点资料，同时仍可回答景区公共问题和其他明确点名的景点。
4. 悬浮“问小灵”和底部“小灵”进入同一个完整数字人页面。
5. 回复完成后可继续发送，发送按钮始终有清晰图标。
6. 感谢、担忧、困惑和普通状态在整轮回答期间有可见差异。

## 3. 非目标

- 不修改地图渲染、路线绘制、GPS 算法或 3D 资产逻辑。
- 不重构 Fay 的 TTS、ASR 和音频播放链路。
- 不删除现有景点数据和旧会话数据结构；迁移以兼容方式完成。
- 不把精确 GPS 坐标长期保存到聊天历史。

## 4. 推荐架构

### 4.1 一个可见会话

游客端使用稳定场景 ID `tour-guide`。`/guide`、`/spot/:spotId` 和悬浮入口都读取同一个 ChatSession 和同一个 Fay username，因此消息历史、游客偏好和多轮上下文连续。

景点变化不再创建新会话，只更新当前 `GuideContext`。清空会话仍由游客主动触发。

### 4.2 位置上下文接口

扩展 `GuideContext`：

```ts
type GuideLocationSource =
  | 'spot-page'
  | 'map-selection'
  | 'route-progress'
  | 'gps'
  | 'route-default'

interface GuideContext {
  routeId?: string
  routeName?: string
  spotId?: string
  spotName?: string
  spotIntro?: string
  spotNarrative?: string
  locationSource?: GuideLocationSource
  locationConfidence?: number
  visitedSpotIds?: string[]
}
```

地图模块只负责更新 `selectedSpotId` 或调用一个场景更新函数，不需要直接操作聊天消息或 RAG。

位置优先级：

1. 当前 `/spot/:spotId` 明确景点。
2. 游客在地图上主动选择的 POI。
3. 路线进度判定的当前站点。
4. GPS 最近景点（仅在距离和置信度达到阈值时采用）。
5. 当前路线默认站点。

手动选择高于 GPS，避免景区定位漂移造成讲错景点。

### 4.3 每轮上下文快照

发送消息时读取最新 `GuideContext` 并生成结构化场景前缀。历史消息保持不变，场景上下文不写死在旧消息中。

寒暄、感谢等短消息继续跳过景点讲解注入；路线、位置、景点、讲解和下一站问题才使用当前场景。

如果游客在问题中明确点名另一个景点，显式景点优先于当前位置。

### 4.4 RAG 场景优先检索

灵山知识库已经带有 `spot_id`、`spot_name` 元数据。检索流程调整为：

1. 从结构化场景前缀或用户问题解析目标景点。
2. 先做现有向量召回，保持对景区公共知识的覆盖。
3. 对目标景点元数据精确匹配的 chunk 加权。
4. 对无景点归属的公共服务、路线和 FAQ chunk 保留正常权重。
5. 用户明确点名其他景点时，按点名景点加权，不按当前位置强行过滤。
6. 结果不足时回退现有全局检索，不白屏、不编造。

这是一种“软隔离”：优先当前景点但不封死公共资料，比每个景点建立独立向量库更易维护。

## 5. 入口统一

移动端悬浮“问小灵”点击后导航到 `/guide`，不再打开独立 `assistant` 浮层。`/guide` 始终展示 Live2D、快捷问题、消息列表和输入区。

从景点详情进入时，页面显示当前景点上下文；从普通页面进入时，使用地图/路线最近一次有效场景。无有效位置时使用路线默认站点，并明确标记来源为 `route-default`。

## 6. 聊天状态修复

### 6.1 发送解锁

`isSending` 表示“本轮消息尚未确认结束”，解除条件为任一条件满足：

- 收到 Fay `_\u003cisend\u003e` 标记。
- 收到 `Data.IsEnd` / `data.isEnd` 完成标志。
- HTTP 请求明确失败。
- 发送超时兜底触发。

收到完整回复后立即解除，不继续等待可能悬挂的 HTTP 请求。HTTP 请求增加 AbortController 超时，防止永久 pending。解除操作幂等，重复回包不会造成状态错误。

### 6.2 发送按钮

给文字单独增加 `.chat-card__send-label`，移动端只隐藏文字标签，不再隐藏 Ant 图标的 `.anticon`。空输入时显示清晰的灰色发送箭头；可发送时显示深绿色底和白色箭头；发送中显示旋转加载图标。

### 6.3 情绪生命周期

发送时根据用户原文生成 `replyEmotionState`：

- 感谢、积极：`happy`
- 担忧、焦虑、难过、投诉：`comfort`
- 困惑、要求解释：`thinking`
- 其他：`normal`

该状态在整轮回答及 TTS 播放期间保持。Fay 的 `Thinking/Speaking` 只表示工作阶段，不覆盖 `comfort/happy/thinking` 的情绪层。百度/Fay 返回的情感结果可补充或修正，但通用 `robot=Speaking` 不能把担忧状态改回普通状态。

音频队列结束后恢复 `normal`。模型缺少某个表情文件时回退到对应动作和状态文案，不影响回答。

## 7. 错误与降级

- 地图未提供位置：使用路线默认站点，不阻断聊天。
- GPS 漂移或置信度低：保留最近一次人工选择/路线站点。
- RAG 没有当前景点命中：回退全局资料并使用现有拒答规则。
- Fay 完成标志缺失：发送超时解除输入，同时显示可重试提示。
- Live2D 表情加载失败：保留文本、TTS 和普通待机状态。

## 8. 测试与验收

### 自动测试

1. 完成标志解析覆盖文本标记和 Data/data 字段。
2. 收到完整回复后 `isSending=false`，可继续发送第二条消息。
3. 超时和请求失败均会解除发送锁。
4. 位置优先级符合“明确页面 > 手选 POI > 路线进度 > GPS > 默认站点”。
5. 点名其他景点时，检索目标覆盖当前位置。
6. 感谢、担忧、困惑、普通文本分别映射正确状态。
7. `Speaking` 不覆盖已确定的 `comfort` 状态。

### 浏览器验收

1. 手机尺寸连续发送至少三轮，不需刷新页面。
2. 空输入、可发送和发送中三种按钮状态均可见。
3. 输入“我有点担心找不到出口”时显示安抚状态；输入“我没听懂”时显示思考状态；输入“谢谢你”时显示微笑状态。
4. 从首页、地图、消费和我的页面点击“问小灵”，均进入同一个 `/guide` 页面并显示数字人。
5. 从九龙灌浴切到灵山大佛后历史对话仍在，新问题优先使用灵山大佛资料。
6. 返回前一个景点或明确询问其他景点时不串台。

## 9. 兼容与协作边界

- 地图同学只需维持 `selectedSpotId`，后续可选提供路线进度/GPS 来源与置信度。
- 聊天改动集中在 `chatSessions`、`useChatStore`、`MobileGuidePage`、`FloatingGuide`、`ChatPanel` 和场景提示构建。
- RAG 改动集中在检索 query 解析与 rerank，不修改知识库原始文档。
- 默认 Live2D 形象和后台形象切换保持不变。
