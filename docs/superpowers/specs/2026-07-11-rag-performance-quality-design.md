# 灵山 RAG 速度、准确率与回复质量优化设计

日期：2026-07-11

## 1. 背景与实测基线

- FAQ 精确命中约 1.6ms。
- `BAAI/bge-large-zh-v1.5` 首次加载与首轮检索约 6.6s。
- 模型热启动后的向量检索与重排约 52ms。
- RAG 自身在线调用 `qwen-plus` 会额外增加约 5.4s，但 Fay 的预启动配置已经使用 `use_llm: false`，生产链路不存在双重 LLM 生成。
- 旧的 `07_regression_check.py` 要求每个问题必须返回向量 `hits`，会把正确的 FAQ 快速命中误报为检索失败，不能直接作为端到端准确率结论。

## 2. 目标

1. 把 embedding 冷启动从游客首轮问答移到服务启动阶段。
2. 保持 FAQ 毫秒级响应与热检索 150ms 内的能力。
3. 降低 FAQ 子串误匹配、景点错配和宽泛问题误命中。
4. 保留显式景点优先于当前位置的规则。
5. 让交给 Fay 的答案与知识片段更短、更直接、引用更明确。
6. 建立能分别评价 FAQ、检索、答案和延迟的真实评测口径。

## 3. 方案比较

### 方案 A：预热 + 保守检索增强（采用）

保留现有向量模型和 Chroma 数据。MCP 启动时同步预热 embedding；FAQ 采用景点与意图一致性约束；普通问题继续使用向量召回和现有 rerank。优点是无需重建知识库，风险低，能直接解决首问慢和 FAQ 评测失真。

### 方案 B：更换小型 embedding 模型

冷启动和单次编码可能更快，但需要重建全部向量数据并重新标定阈值。中文景区专名和文化术语召回存在下降风险，本轮不采用。

### 方案 C：扩大 FAQ 快速通道

重复问题极快，但真实游客问法差异大，维护成本高，也容易产生子串误匹配。本轮只优化现有 FAQ 匹配，不把 FAQ 当作主检索方案。

## 4. 设计

### 4.1 启动预热

- 在 `rag_utils.py` 提供可测试的 `warmup_rag()`。
- MCP 进入 `mcp.run()` 前执行一次预热查询，加载本地 embedding 模型并打开 Chroma collection。
- 预热失败时记录错误但不阻止 MCP 启动，后续仍保留惰性重试能力。
- Hugging Face 保持离线模式，避免首问触发联网检查。

### 4.2 FAQ 匹配质量

- 精确标准化匹配继续最高优先级。
- 子串匹配增加长度比例、显式景点一致性和意图一致性约束。
- 查询明确提到某景点时，禁止命中另一个景点的 FAQ。
- 宽泛关键词重叠不直接返回 FAQ，交给向量检索。

### 4.3 检索与回答

- 保留候选召回数量和现有 rerank，避免为了几十毫秒牺牲召回率。
- 向量查询仅使用清洗后的游客问题；“这一站”类指代问题补入当前景点。
- 显式询问其他景点时，显式景点覆盖当前位置。
- MCP 返回直接答案、最多三段权威上下文和去重引用，减少 Fay 的输入噪声。
- 本地回答控制为先给结论，再给 2 至 3 个要点；不输出检索过程，不重复同一事实。

### 4.4 评测

- FAQ 命中按答案关键词判定，不要求向量 hits。
- 非 FAQ 问题同时检查 Top3 章节命中和答案关键词。
- 单独统计拒答正确性，防止用错误拒答获得表面高准确率。
- 记录 FAQ、冷启动、热检索三类延迟。

## 5. 测试与验收

- 单元测试覆盖预热成功/失败、FAQ 景点冲突、FAQ 精确与安全子串匹配、当前位置与显式景点优先级。
- 现有场景上下文测试保持通过。
- 修正后的回归脚本输出 FAQ 命中率、检索 Top3 命中率、答案关键词命中率和拒答正确率。
- 验收目标：FAQ 路径不高于 10ms；热检索 P90 不高于 150ms；首个非 FAQ 问题不再承担 embedding 初始化时间。

## 6. 非目标

- 本轮不更换 embedding 模型，不重建 Chroma。
- 不更换 Fay 使用的大模型。
- 不通过增加虚构 FAQ 或放宽拒答阈值来制造更高准确率。
- 不修改真实景区资料内容。
