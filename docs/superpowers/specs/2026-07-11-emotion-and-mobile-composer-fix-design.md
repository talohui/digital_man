# 数字人情绪表情与手机端输入区修复设计

## 目标

修复两个直接影响手机端问答体验的问题：

1. 数字人长期保持同一种微笑，无法随用户的负面情绪切换为担忧。
2. 长回复出现后，消息列表会截获滑动，导致用户无法稳定到达输入框和发送按钮。

桌面端布局、现有消息发送协议、音频口型和知识问答逻辑不在本次改动范围内。

## 情绪行为

用户输入是数字人表情的唯一语义来源。小灵生成的回复文本及其情感值不得反向覆盖用户情绪。

表情规则：

- 积极：微笑。
- 中性：微笑。
- 消极、焦虑、担忧、害怕、烦躁、失望或投诉：担忧。
- 困惑：保留现有思考表情。

情绪在用户发送消息时确定，并贯穿本轮回复。通用的 `thinking`、`speaking`、`normal` 传输状态不得覆盖本轮已经确定的担忧或思考表情。本轮回复与音频结束后，数字人恢复默认微笑。

Live2D 表情切换继续使用现有模型资源：微笑使用 `happy` 映射，担忧使用 `comfort` 映射，困惑使用 `thinking` 映射。口型只接管张嘴幅度；不得在 `happy` 或 `comfort` 状态下持续覆盖 `ParamMouthForm`，否则会抹掉微笑或担忧表情的嘴形。

模型异步加载完成后，需要立即应用当前会话的表情状态，避免首次状态更新发生在模型注册之前而丢失。

## 手机端输入区行为

手机端“小灵”页采用一个明确的消息滚动区域，输入区固定在底部导航上方：

- 输入框、麦克风和发送按钮始终可见、可点击。
- 消息列表独立滚动，长回复不得把输入区推出视口。
- 移除阻止滚动继续传递的嵌套滚动设置，避免触摸起点不同导致页面卡住。
- 输入区底部位置同时计算底部导航高度和 `safe-area-inset-bottom`。
- 消息列表保留足够的底部内边距，最后一条消息不会被输入区遮挡。
- iOS/Android 软键盘弹出后，输入区仍位于可视视口内。
- 桌面端聊天卡片保持现有布局，不应用手机端固定定位。

## 组件边界

### 情绪识别

`fayEmotion.ts` 负责从用户原始输入判断积极、中性、担忧和困惑，并输出本轮回复的 `RobotState`。接收 Fay 回复时只读取传输状态，不再用助手回复正文重新推断用户情绪。

### 会话状态

`useChatStore.ts` 在发送时保存本轮情绪状态，在回复及音频期间保持该状态，并在本轮结束后恢复默认微笑。

### Live2D 渲染

`live2dManager.ts` 和 `Live2DStage.tsx` 负责将会话状态映射为模型表情，并保证表情嘴形不被音频嘴形覆盖。

### 手机端布局

`ChatPanel.tsx` 保持发送功能和消息列表职责；手机端样式负责把 composer 固定到导航上方，并让消息区成为唯一需要用户操作的纵向滚动容器。

## 错误与降级

- 未识别到明确负面词或情绪标签时按中性处理，显示微笑。
- 情绪服务缺失、消息未携带情绪字段或字段格式异常时，仍以用户原始文本判断。
- Live2D 模型缺少对应参数或表情 ID 时保持现有静默降级，不阻断问答与音频。
- 不支持动态安全区的浏览器使用固定导航高度作为回退。

## 测试与验收

自动化回归测试至少覆盖：

- “今天玩得很开心”得到 `happy`。
- 普通知识问题得到默认 `happy`。
- “我很担心会迷路”得到 `comfort`。
- “我还是不太懂”得到 `thinking`。
- 小灵回复包含“很高兴”“欢迎”等积极措辞时，不得把已确定的 `comfort` 覆盖为 `happy`。
- `happy` 和 `comfort` 状态不得启用 `ParamMouthForm` 的持续口型覆盖。

浏览器验收至少覆盖 390×844 和 430×932 两种手机视口：

- 注入足够长的回复后，输入框和发送按钮仍在底部导航上方可见。
- 滚动到最后一条消息时，内容不被输入区或导航遮挡。
- 输入并发送消息后，消息列表自动滚到底部。
- 键盘弹出时输入区仍可见。
- 积极、中性、担忧三类文本分别显示微笑、微笑、担忧，并能在连续两轮对话间正确切换。
