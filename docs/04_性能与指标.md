## 3. 数字人问答响应延迟

### 3.1 优化前后对比

| 场景 | 优化前 | 优化后 | 降幅 |
|---|---|---|---|
| 重启后第一条查询(冷启动) | ~28s | **0.67s** | **97.6%** |
| 简单事实问题(灵山大佛多高) | 20–26s | **0.7–2s** | **~92%** |
| 复杂多段问题(梵宫主要看什么) | 20–26s | **6–8s** | **~70%** |
| 网络抖动 SSL EOF 重试 | 偶发 +15s | **0 次** | 100% 消除 |

### 3.2 优化贡献拆分(分项归因)

| 优化点 | 单项贡献 | 累计耗时 |
|---|---|---|
| 切换 qwen-turbo → qwen-plus(非思考流式) | -50% | 20s → 10s |
| 记忆 embedding 改 requests.Session + keep-alive | 消除 SSL 尖峰 | 10s → 8s |
| 注入 planner 的记忆条数 10 → 4 | 缩小提示词,加快首字 | 8s → 5s |
| 灵山 RAG 开 `HF_HUB_OFFLINE` | 消除冷启 24-28s HF Hub 检查 | 28s → 0.67s |
| qwen-plus 45s 心跳保活 | 长 idle 后冷启 TTFT 不再变长 | 锦上添花 |

### 3.3 测量方法
开启延迟埋点:
```bash
LINGSHAN_LAT_DEBUG=1 nohup python main.py start > /tmp/fay.log 2>&1 &
```

各段耗时写入 `/tmp/lat_timing.log`,样例:
```
[01:28:31] 记忆检索耗时 0.66s (skip=False)
[01:28:31] 预启动工具(RAG检索)耗时 0.01s
[01:28:31] 首句送达TTS(首字延迟) 0.67s
[01:28:31] 本轮问答总耗时 0.67s  Q=灵山大佛有多高?
```

## 4. 前端首屏性能

### 4.1 JS 体积优化(生产构建)

| 阶段 | 主 chunk(eager) | gzip |
|---|---|---|
| 起点(全部 eager) | 2,593 kB | **789 kB** |
| 第一轮 lazy + manualChunks | 99 kB | 36 kB |
| **本次最终** | **84 kB** | **32 kB** |

**节省**:首屏 gzip **降低 96%**(789 → 32 kB)。

### 4.2 chunk 拆分明细

| chunk | 大小 | gzip | 何时加载 |
|---|---|---|---|
| `index` | 84 kB | 32 kB | 首屏(必下) |
| `vendor-react` | 143 kB | 46 kB | 首屏(必下) |
| `vendor-router` | 37 kB | 13 kB | 首屏(必下) |
| `vendor-antd-icons` | 66 kB | 23 kB | 首屏(必下) |
| `vendor-antd` | 622 kB | 199 kB | **仅 lazy 路由触发**(admin/spot/desktop map) |
| `vendor-live2d` | 686 kB | 184 kB | **仅切到「小灵」tab 时下** |
| `vendor-analytics` | 186 kB | 62 kB | **空闲帧 idle 加载**(PostHog) |
| `AdminDashboard` | 880 kB | 257 kB | **仅访问 /admin 时下** |
| `ChatPanel` | 12 kB | 5 kB | 进 home / guide / spot 时 lazy(已砍 antd) |

**移动游客真实首屏(不访问 /admin、不进小灵)**:
- 必下:`index + react + router + icons + css` = ~360 kB / **~114 kB gzip**
- idle:`Live2DStage + ChatPanel + TMap`(空闲预热)

### 4.3 二次访问(Service Worker 命中)

| 指标 | 首次 | 二次 |
|---|---|---|
| 网络请求数 | ~12 | **2–3**(HTML + 必要的索引) |
| 总下载量 | ~360 kB | **~5 kB**(HTML SWR) |
| LCP(预估) | 1.2–1.8s | **0.3–0.5s** |

**测量方法**:
1. `npm run build && npx serve dist`
2. 访问一次,DevTools → Application → Service Workers 确认已注册
3. 关闭 tab 重新打开,Network 面板看请求来源是 `(ServiceWorker)`

## 5. 移动端交互性能

### 5.1 sheet 拖拽帧率

| 设备类型 | 优化前 | 优化后 |
|---|---|---|
| iOS / 高端 Android | 60fps | 60fps |
| 低端 Android(骁龙 6 系) | ~30fps,可见卡顿 | **稳定 60fps** |

**优化点**:`useBottomSheetDrag` 钩子内 `touchmove` 期间**直接改 DOM `style.height`**,绕过 React 渲染;松手才 `setState` 触发吸附动画。

**测量方法**:DevTools → Performance → 录制 5s 拖拽 → 看 Main 线程 commit 数量。

### 5.2 INP(Interaction to Next Paint)估计
- 点 sheet handle:< 50ms
- 点景点 chip(展开态):< 80ms(包含 setCenter 一次)
- 发送消息:< 100ms(WS 已通)

## 6. 网络健壮性

### 6.1 WebSocket 自动重连
- 协议:指数退避,1s → 2s → 4s → ... 上限 30s,加 0–500ms jitter
- 触发:`onClose` / `onError` 或 `window.online` 事件
- 实测:杀掉 Fay 进程 → 前端显示"正在重连…" → 5s 内 Fay 重启 → 前端在 1–3s 内重连成功 + 自动 flush 离线发送队列

### 6.2 embedding 网络韧性
- `requests.Session()` + keep-alive,TLS 复用
- 超时由 60s 降为 (connect 5s, read 15s)
- 之前实测 dashscope SSL EOF 重试场景,**优化后 0 次重试**(原来偶发 +15s)

## 8. 满意度算法

| 项 | 公式 | 权重 |
|---|---|---|
| 显式 | 5 星 + 👍👎 加权平均 | **0.65** |
| 隐式 | 完成率 × 0.4 + 停留时长 × 0.3 + 追问活跃度 × 0.3 | **0.35** |
| 平滑 | 贝叶斯先验 = 全局均值,加权样本数 = 5 | 防过敏 |

输出区间 `[0, 1]`,在大屏映射为 0-5 星显示。

API 端点:
- `GET /api/satisfaction/summary` — 全局当前值
- `GET /api/satisfaction/trend?days=7` — 近 7 天趋势

## 9. 资源占用

### 9.1 Fay 后端
- 内存:稳态 ~80 MB
- CPU:空闲 < 2%,问答时段 50–80%(主要 LLM 流式 + TTS 合成)
- 网络:每轮 ~5–15 KB 上行(用户问题 + 上下文),下行 ~10–30 KB(LLM token + TTS 音频)

### 9.2 analytics-server
- 内存:~150 MB(Spring Boot 基础占用)
- 启动时间:~10–20s(maven 第一次冷启)
- H2 文件库:~3 MB(522 条样本 + 索引)

### 9.3 RAG MCP
- 内存:~250 MB(bge-large-zh 模型 + ChromaDB)
- 冷启:首次 1.5s(模型载入),后续每次查询 0.05–0.15s
